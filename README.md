### Command 1 — Constitution

```
/speckit-constitution
```

Paste this prompt:

```
Create governing principles for a safety-critical medication alert monitor
operating in a regulated healthcare environment.

Principles must address:
- Regulatory context: IEC 62304 Class B, ISO 14971, 21 CFR Part 11
- Determinism: pure functions, injected time — never Date.now()
- Traceability: every function traces to REQ-NNN via @satisfies annotation
- Immutable audit: every state transition logged with UTC timestamp + actor ID
- Fail-safe: on error, surface alert — never suppress it
- Testing: one describe block per REQ-NNN, boundary cases required
- TypeScript strict mode, no any types, discriminated unions for state
```

**What you get:** `.specify/memory/constitution.md` — 7 principles,
including explicit prohibition of `Date.now()` in business logic,
mandatory `@satisfies REQ-NNN` annotations, and append-only audit
enforcement. All 16 checklist items pass on first run.

### Command 2 — Specify

```
/speckit-specify
```

Paste this prompt:

```
Overdue Dose Alert with Escalation

OBJECTIVE
A scheduled dose goes unacknowledged with no alert and no audit trail.
In regulated systems, silent failure is the highest-risk failure mode —
it is invisible and unverifiable.

BEHAVIOR
- Detect unacknowledged doses past a configurable threshold (default 15 min)
- Alert the care team with patient ID, medication name, and elapsed time
- Escalate to charge nurse if still unacknowledged after 10 more minutes
- Require authenticated acknowledgment to close any active alert
- Never generate duplicate alerts for the same dose event

CONSTRAINTS
- Every state transition: immutable audit entry with UTC timestamp + actor ID
- On any internal error, surface the alert — never suppress it
- Identical inputs must always produce identical outputs (determinism)
- Anonymous acknowledgment must be rejected and logged

VERIFICATION
- Tests labeled per requirement: describe('REQ-NNN: ...')
- Boundary tests at every threshold value
- Error injection confirms fail-safe behavior (no silent failures)
- Traceability matrix: requirement → function → test → status
```

**What you get:** `specs/001-overdue-dose-alert/spec.md` — generated
on branch `001-overdue-dose-alert` with:
- 4 prioritized user stories with Given/When/Then acceptance scenarios
- 11 numbered requirements (REQ-001 through SAFE-003) in SHALL language
- 5 key entities (DoseEvent, AuditEntry, Alert, Actor, AlertThresholdConfig)
- 6 measurable success criteria
- Edge cases, assumptions, and out-of-scope boundaries
- Quality checklist: all 16 items pass on first iteration

### Command 3 — Plan

```
/speckit-plan
```

Paste this prompt:

```
TypeScript strict mode. Node.js 20 LTS. Vitest. PostgreSQL via adapter.

Architecture constraints:
- State engine: pure functions only — no classes, no shared state
- All time values injected — never read from system clock in business logic
- Each function annotated @satisfies REQ-NNN referencing spec requirement
- Alert dispatch is separate from state evaluation
- Notifier is a swappable adapter (production + test implementations)
- Audit repository is append-only — no UPDATE or DELETE
- Invalid state transitions throw typed errors, never return null silently

Generate: plan.md, data-model.md, research.md
```

**What you get:** Three files generated, plus `CLAUDE.md` updated:
- `plan.md` — architecture decisions, Constitution Check (all 7 ✅)
- `data-model.md` — all TypeScript types, port interfaces, PostgreSQL schema
- `research.md` — 7 architectural decisions with justification

Key decisions made by the AI from the constitution + spec alone:
- `DoseState` as discriminated union — invalid states unrepresentable at compile time
- `nowUtc: Date` injected on every function — `Date.now()` never touches business logic
- `AuditRepository` interface exposes only `append()` — structural append-only enforcement
- `alertDispatcher` separate from engine — errors re-throw, never suppress
- `InvalidTransitionError` + `never` exhaustion — no silent nulls

## The Spec Prompt Format

The `/speckit-specify` prompt above uses a structure that works across
every regulated industry — healthcare, finance, aerospace, automotive,
insurance:

```
[Feature name]          — so SpecKit names the branch and file correctly

OBJECTIVE               — the failure mode, not the feature description
BEHAVIOR                — observable outcomes only, no tech details
CONSTRAINTS             — non-negotiables regardless of implementation
VERIFICATION            — testable criteria, not subjective ones
```

> *"Before you write a spec, answer four questions:*
> *What breaks if this fails? What should it do?*
> *What can never happen? How will you prove it worked?"*

Prompt quality = spec quality = code quality. The discipline is yours.
